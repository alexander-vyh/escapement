# Design — maintainability-verifiers

## Problem Statement

Escapement lands work with no human diff review and no mechanically observed green, and
its own history shows the cost: fix-commit share rose 17% → 70% between May and September
2026, and 49% of repair-touches land on source changed within the previous 24 hours. The
decay is landing-time defectiveness, not architectural rot — measured intra-tree coupling
is flat. After this change, a landing must carry a test that provably failed against
pre-patch code or an explicit waiver, and post-landing repair is attributed back to the
change that caused it.

## Non-Goals

1. **No model judgment in any gate decision path.** A judge model shares the blind spot
   that produced the code, so no LLM verdict may allow or deny a landing here. This locks
   in that intent-level wrongness ("this whole approach is off") is *not* caught by this
   change; it is deferred to human structural review.
2. **No human diff review, now or as a fallback.** The owner has ruled it out. This locks
   in that any defect class only a diff reader can catch stays uncaught until the
   structural-design layer exists.
3. **No coupling or architecture gate in this change.** Measured co-change coupling is
   flat, so gating it now would be a gate for a phantom — it must wait for the repair
   ledger to show recurrence, per `claude/rules/gate-design.md`.
4. **No multi-language pre-patch execution.** Python/pytest only in this increment; other
   ecosystems resolve to "not applicable" and are recorded, not blocked.
5. **No change to plugin-tree distribution.** The 275 duplicated files under `plugins/**`
   are already generated by `tools/render_agent_surfaces.py` and drift-checked in CI;
   touching that is redundant work. See Decisions.

## Capabilities

### New Capabilities

- `prepatch-failure-verification`
- `repair-attribution`

### Modified Capabilities

None. `tdd-gate.py` keeps its current touched-tests-first behavior; the new check is a
distinct, stronger signal at a different point (landing, not first edit).

## Impact

- New: `harness/bin/prepatch_verify.py` (executor and history replay),
  `claude/hooks/prepatch_failure_gate.py` (landing gate), `tools/repair_attribution.py`.
- Consumed: `claude/hooks/_gate_signal.py` (existing signal sink) and
  `claude/bin/gate_signal_analysis.py` (existing recurrence miner).
- `harness/bin/prepatch_verify.py` is vendored into the plugin trees automatically by the
  existing renderer, because the landing gate runs from the installed plugin.

## Riskiest Assumption

We believe **"did any changed test fail against pre-patch production code?" is mechanically
decidable per change, cheaply, without false-firing on honest changes that carry no new
failing test.** We will know this is true when a replay over this repository's 325-commit
history blocks few honest landings while flagging the commits that were repaired within 24
hours. If false, we drop the blocking tier and keep the check as recorded signal feeding
the repair ledger, exactly as `oracle_strength_diff.py` did when its block tier proved
unsafe.

**Embedded alternative (rejected):** mutation testing — kill-score at landing. It answers a
strictly stronger question ("would these tests catch a plausible bug?") and needs no notion
of pre-patch state, but a per-landing mutation run on a Python repo of this size costs
minutes to tens of minutes and is non-deterministic under sampling, which makes it unusable
as a synchronous landing gate. Revisit as an asynchronous nightly signal once the ledger
exists.

## Walking Skeleton

1. Implement `prepatch_verify.py` far enough to answer, for one commit, "which changed
   tests fail when the production hunks are reverted?" and replay it across the full
   history, emitting a per-commit verdict. (60 min)
2. Join those verdicts against the repair-within-24h outcome and report the confusion
   matrix. (30 min)

Done when the replay prints, for this repository, the share of commits carrying a
demonstrably-failing test and the overlap between "no failing test" and "repaired within
24h" — a number that either supports or kills the blocking tier.

## Skeleton Result [VALIDATED] — 2026-09-22

Replayed across all 326 non-merge commits in 286s (0.88s/commit; single-landing cost
measured at 1.4–11s, inside the 60s anti-metric).

| verdict | commits | share |
|---|---|---|
| detecting-failure | 135 | 41% |
| detecting-error | 25 | 8% |
| not-applicable (no production python) | 121 | 37% |
| no-test (production changed, no test changed) | 31 | 10% |
| **vacuous** (every changed test passed without the change) | **14** | **4.3%** |

**The riskiest assumption splits.** Decidability holds: the question is answerable per
change, cheaply, and fires on only 4.3% of commits, so the false-block risk that would
have killed it is absent.

**The rework hypothesis is falsified.** Joined against repair-within-24h:

| oracle state | commits | repaired within 24h |
|---|---|---|
| weak (vacuous or no-test) | 45 | 5 — **11%** |
| a changed test detected the change | 160 | 76 — **47.5%** |

The relationship runs opposite to the assumption. Commits whose tests genuinely failed
pre-patch were repaired within a day *four times more often* than commits with a weak
oracle. The most plausible reading is confounding by risk: substantive changes carry
real tests and also attract repair, while the weak-oracle population is dominated by
small or peripheral changes. Whatever the cause, **a missing failing test does not
predict rework in this corpus.**

Consequences, applied:

1. **The blocking tier is not earned and does not ship.** The gate emits `ask`. This is
   the same conclusion `oracle_strength_diff.py` reached on its own corpus, reached the
   same way — by replay, not by argument.
2. **The gate's value is restated.** It is a correctness floor for the oracle chain:
   `implementation_echo_test_gate`, `outcome_assertion_gate` and `magic_number_echo` all
   reason about tests, and 14 landings put tests in front of them that detected nothing.
   It is *not* a rework predictor and must not be sold as one.
3. **Success criterion 2 loses its mechanism.** Nothing in this change is now expected to
   move the repair-within-7d rate. The repair ledger measures that rate; no gate here
   claims to reduce it. Finding a mechanism that does is open work, and the ledger is
   what will judge any candidate.

Raw per-commit verdicts: `python3 harness/bin/prepatch_verify.py --replay --json`.

## Proof of Delivery

This is done when an agent landing a change in this repository is questioned by
`prepatch_failure_gate` — with the reproduction command and the waiver escape in the
message — whenever every test the change touched still passes with the production change
reverted, and is not questioned when one of them fails; and when
`tools/repair_attribution.py` names the real top-repaired files from git history with
their repair-within-7d rates and the landings that induced them.

It is explicitly NOT "the repair rate falls." The skeleton showed this gate does not
predict repair, and a proof of delivery that claimed otherwise would be the outcome
dishonesty this repository exists to prevent.

## Anti-Metrics

1. **Waiver rate.** If more than half of landings clear the gate by waiver, the gate is
   theater and must be redesigned, not tuned.
2. **Landing latency.** If the pre-patch check adds more than 60s to a landing on this
   repository, it will be routed around and is a failure even when correct.
3. **False blocks on honest changes.** If the replay blocks a majority of commits that were
   never subsequently repaired, the blocking tier does not ship.

## Decisions

- **Revert-the-production-hunks, run the changed tests.** Chosen over checking out the
  parent commit wholesale: the parent lacks the new test files, so the new tests could not
  run at all. Reverting only production files keeps the new tests present and asks the
  precise question.
- **Error counts as detection; only a pass counts as vacuous.** Reverting production hunks
  can leave a test importing a symbol that does not exist yet. That test is coupled to the
  change, which is the property being checked. Failure and error are reported separately so
  the number stays honest.
- **Plugin-tree duplication is out of scope — the original premise was wrong.** The design
  first claimed the 275 duplicated files under `plugins/**` were hand-synced and proposed
  generating them. `tools/render_agent_surfaces.py:663-703` already generates them and
  `.github/workflows/tests.yml:52` already drift-checks them in CI; the one apparent
  divergence (`skills/beads-execution/SKILL.md`) is CRLF normalization by the renderer, not
  semantic drift. Building a generator would have duplicated an existing owner — the exact
  defect this change exists to reduce.
- **Signal before gate for repair attribution.** The ledger ships as measurement only. Gates
  derived from it wait for observed recurrence.

## Risks & Trade-offs

- **Replaying history runs this repository's own tests** → the replay redirects `HOME` to a
  temporary directory so gates that read `~/.claude` cannot write into the real home.
- **Changes with no production hunks** (docs, generated surfaces, pure test additions) →
  classified not-applicable and recorded, never blocked.
- **Commit-subject repair classification is coarse** → the ledger carries its classifier and
  is validated against known ground truth in `--self-test` rather than assumed correct.
- **Repair begets repair.** The first ledger run shows fix commits among the top inducing
  landings, so attribution chains through repair work. Accepted and reported as-is; it is a
  finding, not a defect in the measure.
